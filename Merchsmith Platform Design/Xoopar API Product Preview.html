What the full export settled

1It is the right endpoint — I was wrong about that

On three records I concluded the API was serving trading data only. The full export shows both live side by side: 223 records carry the complete picture (name, images, description, category, decoration methods and prices, certifications, dimensions) and the remaining 965 carry price, stock and identifiers alone. Not one record has images without also having a name, so the split is clean — the described 223 are the Xoopar own-brand range, and it matches the 223 products we already imported from their PIM export.

2The quantity suffix is a real price break

Across all 1,188 records, GIFT_BRONZE_T3_1000 differs from the base in 184 — so it is the price at 1,000 units, not a duplicate. It reads €0 on many records, which means unpriced rather than free, so the importer ignores zeros: 167 products end up with a genuine break. The three samples you sent first happened to be flat, which is why it looked like a duplicate.

3Every record now prices and names itself

Using the tier as the price source, 1,174 of 1,188 price successfully; the 14 that don't have €0 in the attribute and list as POA. Falling back to short_description for a name clears the nameless products entirely — nothing lands in the store as a bare code any more. The band is still worth confirming: BRONZE tier 3 is the only band in this export, so if better bands exist they aren't being returned to this account.

Adapter changes made

✓
Tier pricing. Price now reads GIFT_<band>_T<n>_ (falling back to the legacy price attribute), with any quantity-suffixed sibling becoming a price break. Zeros are treated as unpriced. The import warns which band priced the feed.
✓
Money attributes were being dropped. The reader handled {amount, unit} measurements but not [{amount, currency}] money arrays — so every decoration run price and setup fee silently came through as null. Fixed: 185 products now import their print costs and setup fees.
✓
French method names. The live API returns "Numerique", "Tampographie", "Sérigraphie", "Gravure laser". Only English names were mapped, so pad printing was landing as digital. Now mapped properly.
✓
Compliance fields hold documents, not booleans. ce_eu, rohs_eu, reach_eu, msds_global, un38_3_global contain PDF report URLs — the old code pushed the entire URL in as a certification name. Now the standard's name shows on the product and the report is kept as an attached document.
✓
Weight unit. weight_g sends KILOGRAM units despite the name (0.0850 = 85 g), so weights were 1,000× out. Normalised to grams, with values above 1 treated as grams typed into a kg field — which is what the PopGrip records were doing at "19.05".
✓
Name fallback to short_description after retail_name and designation.

Still open

  • Confirm the price band. BRONZE T3 is the only one in this export. If Merchsmith should be on a better band, the API needs to return it for this account.
  • The 965 trading-only records. Many are licensed goods (Disney and Marvel PopGrips, with ASINs and no decoration data) which can't be branded — the platform's core proposition. Worth deciding whether they belong in the range at all, and if so they need their own product type with branding switched off.
  • Images need authentication. The media-files URLs sit behind the same credentials as the API, so they won't load in a browser directly — production will need to proxy or re-host them. That's why the image above may not render here.
  • One data fault to raise: record 100483 is named "…(PG) BK" (black) but product_colors says Blue. There will be others; the colour mapping tool's coverage table will surface them once imported.
