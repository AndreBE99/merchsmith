The normalised product feed

How product data from many sources — supplier APIs (XD Connects et al.), CSV uploads, and manual entry — is mapped into one canonical product model that the whole platform reads. This is the contract between the data layer and everything the prototype shows (Store, branding builder, price matrix, stock).

This page is for you (product owner) and the developer to agree the data contract before the integration is built. The prototype already reads a model shaped like this (window.STORE), so the UI is proven — this defines the real version behind it.

1The principle: normalise once, read everywhere

Every source has its own shape. Rather than teach the app about each one, each source gets a small adapter that maps it into the single canonical model. The app only ever knows the canonical model — so adding a new supplier later is just a new adapter, no UI changes.

2The canonical product model

One product = one record with nested variants, decoration options, price scales and stock. Illustrative JSON below — this is a core sample, not the full field set. Expect more fields as the product page is finished (e.g. extra specs, packaging, branding artwork refs, compliance docs). Each field also carries a visibility rule — some data (cost, margin, supplier refs, full stock) is distributor-only and never sent to the customer's view; the API/serialiser filters by role.

3Mapping XD Connects → canonical

XD's feed (Xindao V7) is five files that join on the item/model code. Each maps onto part of the canonical model:

XD feed fileKey native fields→ Canonical target
ProductsitemCode, modelCode, name, description, category, colour, material, dimensions, image URLsid, sku, name, description, category, material, dimensions, images, variants[]
ProductPricesitemCode, qty-scale → unit pricepriceBreaks[] (blank unitCost)
PrintDatatechnique, position, max colours, print area dimsdecoration[].method / positions[] / maxColours
PrintPricestechnique → setup + per-colour cost by qtydecoration[].setup / runCost[]
StockitemCode, stock level, incoming + datesstock[].onHand / incoming[]
XD's feed is a tokenised file download for server-side use, rate-limited (~1 fetch / 15 min) and not CORS-enabled — so it can never be read by the browser. The sync job lives on the back end.

4Other sources

  • API  Other supplier feeds (PF Concept, Mid Ocean…) — one adapter each, same target model. Most promo suppliers publish a similar 4–5 file structure.
  • CSV  CSV upload — for suppliers without an API, or the distributor's own lines. We agree a CSV template whose columns map 1:1 to the canonical fields (one row per variant/price-break, or a flat sheet the importer pivots). Distributor uploads → preview → commit.
  • MANUAL  Manual products — added in-app (we built this in the supplier profile). Writes straight to the canonical model.

5Sync, identity & images

  • IDs: our canonical id is source-prefixed (xd-P705.991) so codes never collide across suppliers. The supplier's own code stays in sku.
  • Sync cadence: scheduled job (e.g. nightly full + hourly stock) respecting each source's rate limit. updatedAt drives change detection.
  • Images: synced to our CDN on import (never hotlinked from the supplier) — faster, stable, and survives the supplier changing URLs.
  • Pricing note: the feed carries cost only. Markup, discounts, delivery and the customer sell price are applied by our pricing engine (see the Price Matrix spec) — never stored in the feed.
  • Soft-delete: products that drop out of a feed are flagged inactive, not hard-deleted (preserves order history).

6Open questions for the developer

Hosting / stack — where does the sync job + DB live (e.g. a scheduled worker + Postgres)? Confirms how feeds are pulled.
Sample payloads — can we get one real product object from each of XD's 5 files, so the adapter's field names match exactly from day one?
CSV template — flat one-row-per-product (importer pivots variants/breaks), or multi-sheet? I can draft the template once you decide.
Variant model — is colour×size enough for all suppliers, or do some have other axes (e.g. capacity, finish)? Affects the variants[] shape.
Decoration matching — do we map every supplier technique to our shared method list (screenprint, DTF, pad, embroidery, laser), or keep supplier-native names too?

7Fields captured vs surfaced

Ingest everything XD provides into the canonical model now — even fields the UI doesn't show yet — so we never need a re-sync to surface them later. Surfaced now = where it appears in the platform today (incl. the new Store distributor view panel); Future location = the planned home once those screens/stages are built.
