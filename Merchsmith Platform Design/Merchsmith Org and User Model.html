Organisation & user model

The data structure behind who exists on the platform and who can see what. This is what the site map can't show — it covers navigation; this covers entities, relationships, roles/permissions and multi-tenant data isolation. Build the database and auth from this.

Pairs with the Site Map (navigation) and the Product Feed Spec (data). Use all three together for the build.
Note: entities/fields shown are the core set — not exhaustive. Every entity can take additional fields (e.g. a User also has timezone, last-login, notification prefs, 2FA, permissions overrides). Treat these as the spine, extend freely.

1Entity hierarchy

Merchsmith (the platform) has many Distributors — each Distributor is a tenant: an isolated world. Under a Distributor sit their Customers, Suppliers and internal Team. Every organisation type — including the Merchsmith Platform itself and Suppliers — has its own Users/Team (with role-appropriate access).

2Core entities & key fields

Organisation

  • id primary key
  • type distributor · customer · supplier
  • parentDistributorId tenant owner (null for distributor)
  • name, domain, logo, address
  • status active · pending · suspended
  • settings JSON (markup, discounts, lieu, colourway…)

User

  • id primary key
  • orgId → Organisation
  • teamId → Team (customer users)
  • name, email, phone, jobTitle, avatar
  • role see §3
  • status active · invited

Team / Department

  • id
  • customerOrgId → Organisation
  • name Marketing · HR …
  • projects & orders can scope to a team

Supplier link

  • id
  • distributorId + supplierOrgId
  • kind product · branding · both
  • leadDays, daysInLieu (override)
  • paymentTerms
A Supplier can serve more than one distributor, but each distributor only sees their own link to that supplier (their lead times, terms, contacts). The supplier record's shared catalogue is platform-level; the relationship is per-tenant.

4Multi-tenancy & data isolation

  • The Distributor is the tenant boundary. Every row (customer, supplier link, project, order, product price, comment) carries a distributorId; every query is scoped to it.
  • Customers never see each other. A customer user only sees their own org's projects/orders — and, where scoped, only their team's.
  • Suppliers never see other suppliers or the end customer's identity beyond what an enquiry exposes.
  • A customer using two distributors has two separate accounts — no shared data, separate logins (as agreed).
  • Platform Operators sit above tenants and only enter one via ghosting, which is audit-logged.
  • Identity lockup follows context: Customer × Distributor when a customer logs in; Customer × Distributor when the distributor opens that customer; Distributor alone on their own dashboard; Merchsmith for the operator.

6Open questions for the developer

Auth model — one global identity that can belong to multiple orgs (with an org-switcher), or strictly one-account-per-org (as the customer-with-two-distributors rule implies)? This shapes the whole auth schema.
Role granularity — fixed roles (as in §3) or configurable per-permission? Recommend fixed roles for v1, custom later.
Supplier ↔ customer permission — still open from earlier: can a customer ever add/see a supplier contact? Currently no.
Team scoping — are budgets/credit limits set per customer org, or also per team?
Audit trail — confirm what's logged (ghosting, approvals, price changes, status promotions) and retention.
